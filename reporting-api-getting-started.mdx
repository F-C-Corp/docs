## Overview

Exports are asynchronous. You create an export job, poll it until the artifact is ready, then download the file before the signed URL expires.

Germany (KassenSichV) has two export types today, and a tax audit typically asks for both. Additional types for other regimes will be added as those regimes are enabled.

## Export types

Each type has **its own create endpoint**, because the parameters, the meaning of `register_id`, and the error codes differ per type.

| Type | Create | Retrieve | Description |
| --- | --- | --- | --- |
| DSFinV-K | `POST /exports/dsfinvk` | `GET /exports/dsfinvk/{exportId}` | Germany (KassenSichV) — archive containing the CSV files, `index.xml`, and GDPdU DTD mandated by the German tax authority. Describes the **cash register**. |
| TSE | `POST /exports/tse` | `GET /exports/tse/{exportId}` | Germany (KassenSichV) — the signed Log Messages themselves, per BSI TR-03153. Describes the **security device**. |

Both require `register_id`, but it means different things:

- **DSFinV-K** is per-register. `register_id` *is* the scope: the archive covers exactly that register.
- **TSE** is per-device. `register_id` *resolves* which security device to export, and the archive covers that device in full. A Swissbit TSE is shared by every register at the same business premises and offers no filtered export, so a TSE archive contains the log messages of the other registers on that device too. A window spanning a device change resolves to both devices.

Retrieving is type-specific too, so an id that names an export of a different type returns `404`. The path asserts what you believe you are reading rather than handing back a differently-shaped response.

<Note>
  The untyped `POST /exports` (with a `type` field in the body) and `GET /exports/{exportId}` still work but are **deprecated**. Use the type-specific endpoints above; they document their own parameters, responses and errors.
</Note>

## Requesting an export

Every export requires a `register_id` and a time range (`from`, `to`). The type comes from the path, not the body.

```bash
curl -X POST https://sandbox.api.openfiskal.com/v1/exports/dsfinvk \
  -H "Authorization: Bearer of_test_deu_abc123..." \
  -H "X-OpenFiskal-Merchant: merchant_01HXYZ" \
  -H "Content-Type: application/json" \
  -d '{
    "register_id": "reg_01HABC",
    "from": "2026-03-01T00:00:00Z",
    "to": "2026-03-31T23:59:59Z"
  }'
```

The resulting TAR archive contains the full DSFinV-K dataset: `cashpointclosing.csv`, `transactions.csv`, `lines.csv`, `payment.csv`, `vat.csv`, and the other mandated files alongside `index.xml` and the GDPdU DTD.

For the TSE export, the only change is the path:

```bash
curl -X POST https://sandbox.api.openfiskal.com/v1/exports/tse \
  -H "Authorization: Bearer of_test_deu_abc123..." \
  -H "X-OpenFiskal-Merchant: merchant_01HXYZ" \
  -H "Content-Type: application/json" \
  -d '{
    "register_id": "reg_01HABC",
    "from": "2026-03-01T00:00:00Z",
    "to": "2026-03-31T23:59:59Z"
  }'
```

That TAR contains one file per Log Message, named exactly as the security device named it, plus the device's `info.csv` manifest and its X509 certificate chain. Every `.log` entry is byte-for-byte what the device produced; only the containing archive is assembled by OpenFiskal, because a device export is incremental and no single one spans a requested period.

### Synchronous validation at create time

Both create endpoints validate the request before enqueuing the job, so a request that cannot succeed fails immediately rather than as a failed job. The window is silently clamped to the register's fiscalized lifetime (`max(from, fiscalized_at)` to `min(to, decommissioned_at ?? now)`), which is why the `from` and `to` in the response may be narrower than what you sent.

**`POST /exports/dsfinvk`**

| Status | Code | When |
| --- | --- | --- |
| `400 bad_request` | `register_id_required_for_dsfinvk` | `register_id` is missing |
| `422 validation_error` | `validation_error` | Register is not on the KassenSichV regime |
| `422 validation_error` | `export_dsfinvk_no_closed_sessions` | Clamped window contains no closed sessions on the register |
| `422 validation_error` | `export_dsfinvk_build_pending` | A closed session in the window has no DSFinV-K cashpoint-closing yet — retry shortly |

**`POST /exports/tse`**

| Status | Code | When |
| --- | --- | --- |
| `400 bad_request` | `register_id_required_for_tse` | `register_id` is missing |
| `422 validation_error` | `validation_error` | Register is not on the KassenSichV regime |
| `422 validation_error` | `export_tse_no_device_in_window` | The register was not bound to any security device during the clamped window |
| `422 validation_error` | `export_tse_archive_pending` | No Log Messages are archived for that device over the window yet — retry shortly |

`export_dsfinvk_build_pending` and `export_tse_archive_pending` are both transient and both mean "the pipeline has not caught up". Retrying shortly is the right response. They exist so you never receive an archive that silently stops early.

### Polling and download

Poll the retrieve endpoint for the type you created — `GET /exports/dsfinvk/{exportId}` or `GET /exports/tse/{exportId}`.

If validation passes, the job is enqueued and the response carries `status: "pending"`:

```json
{
  "id": "exp_01JDEF",
  "type": "dsfinvk",
  "status": "pending",
  "register_id": "reg_01HABC",
  "from": "2026-03-01T00:00:00Z",
  "to": "2026-03-31T23:59:59Z",
  "download_url": null,
  "error": null,
  "created_at": "2026-03-31T12:00:00Z",
  "completed_at": null
}
```

Poll `GET /exports/{exportId}` until `status` reaches `completed`:

```json
{
  "id": "exp_01JDEF",
  "type": "dsfinvk",
  "status": "completed",
  "register_id": "reg_01HABC",
  "from": "2026-03-01T00:00:00Z",
  "to": "2026-03-31T23:59:59Z",
  "download_url": "https://storage.googleapis.com/...",
  "error": null,
  "created_at": "2026-03-31T12:00:00Z",
  "completed_at": "2026-03-31T12:00:42Z"
}
```

If the job fails, `status` is `failed` and the response carries an `error` object:

```json
{
  "id": "exp_01JDEF",
  "type": "dsfinvk",
  "status": "failed",
  "error": {
    "message": "Build pipeline failed for session ses_01HZ.",
    "details": null
  },
  "completed_at": "2026-03-31T12:00:42Z"
}
```

## Retention

`download_url` is a signed URL that expires **7 days** after `completed_at`, matching the bucket lifecycle rule that deletes the artifact at the same point. Copy each artifact to your own durable storage before then. If the URL has expired, you can re-create the export for the same window.

## Limitations today

- DSFinV-K and TSE are the export types currently available, both Germany (KassenSichV)
- There is no list endpoint; track the export IDs you create, along with their type
- A TSE export cannot be narrowed to one register on a shared device — see the note under [Export types](#export-types)
- AT (DEP7/RKSV) and IT (RT) export types will be added when those regimes ship
